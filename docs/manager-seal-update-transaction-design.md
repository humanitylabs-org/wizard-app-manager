# Accepted installed revision — controller review draft

**Design only. No product implementation, migration, acceptance or new owner gate.** Production bytes remain `3116f500f4d7df959a9f4d586dec4f9a9b7564b5`. The original manager contract includes routine V1→V2→V3 updates; a permanent second-stage refusal is not the finished product. Review this transaction before changing production or replacing the saved bundle.

Do not attach `clearPrevious()` to any of these existing callbacks. DB version alone, generated files, a cached SSE, command success, or RPC completion can acknowledge a revision that failed finalization or was superseded. Current schema-2 policy does not prove whether its current revision was installed; never infer that on migration.

## REUSE / EXTEND / NEW

REUSE trusted definition hashes, envelope validation, sticky enrollment, mandatory effective Compose validation, current-grants projection, real queue and update command. EXTEND the **existing** per-URN cross-process fence to the complete enrolled update and terminalization; nested Compose calls reuse an unforgeable in-process owner context, not recursive mkdir or public flags. NEW minimal durable transaction/accepted-revision records and a crash-reconciliation protocol. No new approval endpoint, no policy erasure, no independent watchdog/parallel manager.

## Proposed state and commit protocol

1. Separate `accepted` (last manager-committed installed definition) from reviewed `candidate`, with immutable definitions retained for the currently accepted revision and one in-flight rollback predecessor. Retain `policyGeneration`, `acceptedTxn`, and optional `pendingTxn` bound to URN, real requestId, expected accepted hash, exact candidate hash, target catalogue/version hash, previous running/stopped state, persistent snapshot location/digest and monotonically increasing generation. Enrollment still cannot downgrade to ordinary.
2. Schema-2 import is conservative: preserve both definitions byte-for-byte and mark installed acceptance **unknown**; require normal manager-owned reconciliation under the fence, with exact installed recipe and running/stopped deployment identity evidence. If ambiguous, refuse another stage with actionable recovery, not unsafe automatic anchor eviction and not a newly invented owner approval. Defining the legacy reconciliation proof is a review item, not permission to equate latest staged with installed.
3. Under the same per-URN fence, admission CAS-binds request and candidate to the accepted hash/generation; persist and fsync a journal plus private persistent old files/env/subnet snapshot BEFORE target file changes. Staging during a pending transaction refuses/retries; duplicate identical request returns its exact durable receipt. Different request/generation cannot adopt an old success. A trusted stage may replace only an unclaimed candidate, never the pending target or accepted anchor.
4. Execute the existing prepare/pull/down/up sequence with the frozen target bytes, not two unconstrained fresh reads of mutable catalogue. Reject changed target before destruction. Use current security/storage/share authorization at **each** launch, including rollback. Reuse validated per-launch snapshots for nested down/stop. Add an owner-aware internal API rather than re-entering `MandatorySeal.exclusive()` and deadlocking. Ordinary unenrolled behavior stays unchanged.
5. After target deployment, complete required config/env work INSIDE the transaction owner, without a second queued command waiting for its own held mutex. Verify exact target definition and generated/effective hashes; for running apps verify owned container IDs/runtime+mandatory networks and current grants, for stopped apps prove no start and exact installed files. Persist a deployment witness tied to the transaction/generation. This is still not accepted.
6. In one PostgreSQL transaction, CAS the pending transaction/generation and write app version/config/subnet/status plus an immutable accepted-revision receipt and policy-finalization outbox row. Rollback/config-finalization failure BEFORE this DB commit restores V1 through the original rollback path. Do not discard the recovery snapshot at command return. Do not emit public success here while policy publication remains pending.
7. Under the still-held fence, materialize the DB-committed accepted receipt into trusted manager-owned policy by fsync-temp, atomic rename, fsync-parent. Set accepted=V2 and retain V1 rollback definition. CAS both prior policy generation and transaction ID; never unconditionally clear previous. Complete the outbox idempotently; only then expose terminal success/release the fence/retire the snapshot. All launch/stage paths refuse an unresolved publication. This is a cross-store protocol, NOT a filesystem+DB atomicity claim.
8. Next trusted V3 stage CAS-binds to accepted V2. It may replace the obsolete V1 rollback slot with V2 **only because the durable V2 receipt is finalized**, not because V2 was staged or its files happen to exist. V3 failure restores V2. Repeat without cumulative anchors or additional human approval. Keep a bounded durable terminal receipt for exact duplicate outcomes; never derive attempt A from latest app status after attempt B.

## Crash, restart, concurrency and revocation

| Interruption / race | Required behavior |
| --- | --- |
| Before journal/snapshot durable | No destructive effect or new accepted hash. |
| After snapshot / before down | Keep accepted V1; startup resolves pending generation before serving lifecycle mutations. |
| After down / target up / before DB commit | Journal remains pending; no V3 stage. Reconcile exact identities and snapshot; restore V1 or retain explicit recovery-required failure. No blind queue redelivery/up replay from timeout. |
| DB commit succeeded, policy rename failed / process died | Durable outbox proves V2 accepted by DB; block starts/stages until policy is materialized under the fence. Do NOT roll back a committed DB transaction by restoring a stale V1 record. Do not rerun destructive update. |
| Policy published, terminal receipt/outbox delivery failed | Idempotently reconcile same txn and publish terminal state; no repeated up or new transaction. |
| Rollback failed | Retain both definition authorizations, journal and protected snapshot; stopped/recovery-required, no accepted V2 and no V3 staging. Failed receipt remains failed. |
| Daemon dies holding mkdir lock | Preserve fail-closed fence. Do not age-steal it. Existing stopped-manager recovery must prove all owners absent; startup journal recovery needs a reviewed owner-generation mechanism. A new implementation must not pretend an ordinary restart automatically releases this lock. |
| Two managers / trusted CLI stage | Same cross-process per-URN admission fence and CAS generation; one independently eligible winner, loser no mutation. In-memory mutex is insufficient. |
| Restore/reset/uninstall/restart/share recreation races update | Every same-URN mutator participates in transaction ownership; corrupt-policy stop/down remediation remains available without acknowledging success. Audit lock order before coding. |
| Share revocation while updating / rolling back | Never restore grant snapshots. Acquire existing storage/grants serialization inside per-URN transaction scope for each launch. Use current denied/grant state. Terminal witness records grant generation, revalidated at commit/publication. Revocation ordered after that witness must itself recreate the accepted revision without revoked mounts; before it must be visible to target/rollback launch. No old managed target may return via retained definition. |

**Lock-order review:** current mandatory path takes seal → storage serial; share controller currently changes storage state and later recreates. Standardize per-URN owner → storage/grants fence → short DB transaction; never hold a DB transaction while awaiting queued work/Docker. Do not reverse storage→seal while another caller holds seal→storage. Grant changes spanning multiple URNs need deterministic URN ordering or split durable invalidation and recreation, not ad hoc nested locks. Snapshot retention and failed-rollback cleanup stay owner-bound.
