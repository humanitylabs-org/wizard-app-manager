## Trusted enrollment and boundary

Only a trusted host administrator, as the manager's UID, may invoke `bun packages/backend/src/cli/enroll-mandatory-seal.ts DATA_DIR APP_URN REVIEWED_COMPILED_JSON`. The JSON is the existing Agent Service compiler's provider-held-key `private_seal.apply` result, reviewed separately, not a captured optional configuration. There is no HTTP enrollment, revision or unenrollment route. An existing enrollment cannot be replaced by this utility, including after a partial/corrupt write. Recovery/revision of manager-owned state stays separately gated. The enrollment directory is sticky; missing/corrupt policy content does not turn the app into an ordinary app. Trusted-host deletion of the entire state namespace is outside the mutable-catalogue/optional-config threat model and is not represented as defended.

Compose config is resolved both for the required document alone and for all ordinary/optional inputs plus the mandatory overlay. Whole-map `!override` removes extra services and public networks, not only the client's array entries. Compare the effective critical sections, then write a private, dollar-escaped resolved snapshot and pass ONLY that snapshot to launch. Keep the existing storage grant lock across validation, destructive callback and `up`. A standalone update `prepareApp` also validates before backup/stop/down. Invalid policy cannot call a restart callback. Other direct Compose activation shortcuts are refused for enrolled apps. Stop/down remain available for remediation even if policy is corrupt.

Normal app backups copy app-data, installed app and user-config folders; they do not own `state/mandatory-seals`. Do not extend that authority. This first policy is intentionally not an automatic mutable runtime-upgrade or dynamic grant-policy migration system; changing approved runtime/grant topology needs separate reviewed policy admission.
